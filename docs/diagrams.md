# Diagram standard

Every diagram on this site is a static SVG that was rendered at BUILD time by the
D2 CLI, from a Python description, and committed to `assets/diagrams/`. There is
no diagram library, no client JavaScript, and no CDN request. The page ships an
`<img>`.

That is the whole standard. If a diagram needs something extra to look right,
the diagram or the generator is wrong, not the standard.

## The pipeline

```
scripts/diagrams/build.py   the DIAGRAMS dict IS the diagram source
        |  python3 scripts/diagrams/build.py
        v
d2 CLI (--layout=dagre)     renders one SVG per diagram per theme
        |
        v
open_icon_label_gap()       post-process, see below
        |
        v
assets/diagrams/*.svg       committed source assets
        |
        v
{{< diagram >}} shortcode   resolves <name>.<theme>.svg, emits <img>
```

The generated SVGs are **committed**, not built by Hugo. That is deliberate:
the diagram content is authored in Python, not in Markdown, so the SVG is a
source artefact the way a hand-written `.svg` would be. Hugo consumes it, it
does not produce it. If the SVGs were generated during `hugo build`, every
build would need a working D2 binary and the build would stop being
deterministic.

## Adding or editing a diagram

1. Edit the `DIAGRAMS` dict in `scripts/diagrams/build.py`. Each entry is a
   list of `(key, label, shape, icon_role)` nodes plus a list of `(from, to)`
   edges. The key is a D2 identifier used only inside the generated `.d2`; the
   label is the reader-facing text.

   ```python
   "07-example": dict(dirn="down", nodes=[
     ("a","Source systems","cloud","cloud"),
     ("b","Query and filter","rectangle","filter"),
     ("c","Object storage","cylinder","storage")],
     edges=[("a","b"),("b","c")]),
   ```

2. Run the generator **from the repo root**:

   ```
   python3 scripts/diagrams/build.py
   ```

   Not from inside `scripts/diagrams/`. The icon paths it emits
   (`assets/icons/<theme>/<role>.svg`) are relative, so the working directory
   decides whether they resolve.

3. Commit the regenerated `assets/diagrams/*.svg` alongside the Python change.
   A diff in `build.py` with no diff in the SVGs means the generator did not
   actually run, or it wrote somewhere you are not looking.

4. Add the shortcode to the article, on its own line, never mid-paragraph:

   ```
   {{< diagram name="07-example" caption="What the reader should take away." >}}
   ```

   Confirm the current argument names in `layouts/shortcodes/diagram.html`
   before relying on this snippet.

5. Verify. See below.

The `diagrams: true` front matter key no longer loads anything, because there is
no library to load. Whether it still gates anything (figure styling, asset
resolution) is a question for the shortcode and its CSS. Do not remove it from
an article until you have checked.

## The contract with the shortcode

| Item | Rule |
|---|---|
| Filename | `assets/diagrams/<name>.<theme>.svg` |
| Files per diagram | Two. One per theme. |
| `<name>` | The key in the `DIAGRAMS` dict, and the `name` the shortcode is called with. They are the same string. |
| `<theme>` | `light` or `dark`. Nothing else. |

The shortcode uses `errorf`, so a call site that names a diagram which was
renamed, deleted, or never generated **fails the Hugo build**. That is the
intended behaviour and it is the main reason to keep the filename contract
strict: a broken diagram reference is a red build, not a silent hole in the
page. Do not "fix" it by relaxing the shortcode.

## Icons

Icons are [Lucide](https://lucide.dev) outlines, 24x24 viewBox, single stroke,
`stroke-width 2.75`, generated by `scripts/diagrams/gen_icons.py` with a colour
argument, once per theme:

```
python3 scripts/diagrams/gen_icons.py "#7C3A0A" assets/icons/light
python3 scripts/diagrams/gen_icons.py "#FFD8A8" assets/icons/dark
```

**Lucide is ISC licensed. Keep that attribution wherever the icons are
referenced.**

Fifteen icons are defined in the `P` dict in `gen_icons.py`. To add a new one,
add a Lucide SVG path (the inner markup, no `<svg>` wrapper) to `P`, then
regenerate **both** theme sets. A role name with no file in
`assets/icons/<theme>/` renders as a missing image, so the two must stay in
step.

| Name | Use for |
|---|---|
| `cloud` | an external system or party at the boundary |
| `search` | query work, asking a source for data |
| `filter` | a filter stage, narrowing a set |
| `cpu` | a compute unit, a service doing work |
| `package` | the step that produces an artefact |
| `database` | a datastore, a stored body of records |
| `chart` | analytics, a derived dataset |
| `server` | a service, a deployable |
| `monitor` | a consumer, a client, a reader |
| `storage` | object storage, a bucket, a CDN origin |
| `swap` | a handover, a publication, a transfer |
| `shield` | a verification or control step |
| `save` | a write |
| `check` | a gate, a condition being confirmed |
| `sliders` | a configurable or central control |

Two settled arguments, so nobody reopens them:

- **Registry icon sets were rejected.** They are filled rather than outlined, and
  a filled glyph does not articulate at the size these render.
- **2px strokes were rejected** as too thin. `2.75` is the compromise. Do not
  "tidy" it to 2.

Icons are the same family as the TOC chevron, which is why Lucide was chosen.

## Shape, icon, label: three independent channels

This is the reading contract, and it is why all three exist:

| Channel | Carries |
|---|---|
| **Shape** | Category. `rectangle` = process, `cylinder` = storage, `hexagon` = verification or control, `cloud` = external. |
| **Icon** | Identity. Which specific thing this is. |
| **Label** | The explanation. |

They are independent on purpose. `05-cutover` ends with a `rectangle` carrying a
`database` icon labelled `Pipeline only`: the shape slot was taken by the
process, the icon says what it now is, the label says what it means. Collapsing
any two of them into one channel loses information.

### Node groups: distinguishing two states in one chain

A `group_of` mapping on a diagram styles nodes by role, so a before/after figure
can show the change in the drawing instead of only describing it in a caption.
`04-before-after` marks the first three nodes `retired` and the last four
`current`: retired nodes get a dimmed fill and a dashed border, current nodes
stay solid, and the edge crossing from `retired` to `current` takes the accent
stroke. Fills are per theme (`GROUP_FILL`), because a light-mode dim is
unreadable on the espresso surface.

Without it that figure was seven identically styled boxes and "Forecast
service" appeared twice with nothing marking which copy was old — the caption
promised a contrast the drawing did not contain.

**Do not reach for D2 containers to group nodes.** They were tried and are
worse here: dagre stacks the containers, which took the figure from 1500px to
2307px tall, and `direction: right` blew the aspect ratio out to 6.69. Per-group
node styling gives the same distinction at the original size.

## Labels

**Every node carries a meaningful text label. This is a hard rule.**

The label is the EXPLAINER. An icon is not self-evident to a reader who has
never seen that glyph, and it is worse for a screen reader, which gets an
unlabelled graphic. A diagram whose meaning lives only in its icons is a
diagram that fails the reader and fails accessibility at the same time.

Do not strip labels to "let the icon speak". The icon speaks to nobody.

A numbered-label scheme (bare `1`, `2`, `3` with the meaning pushed into a
legend) was tried and rejected by the author. It reads as a puzzle, and the
legend is one more thing to keep in sync.

- **Node labels: 1 to 3 words, no trailing punctuation.** `Query and filter`,
  not `Query stage with filter pushdown`.
- **Edge labels: 2 to 4 words, and currently unused.** The generator emits no edge
  labels at all. If you add one, keep it short: a long edge label is a layout
  collision you cannot fix afterwards.
- **One idea per diagram.** A diagram that needs a paragraph to read is a
  paragraph.

## The icon-to-label gap post-process

`open_icon_label_gap()` in `build.py` runs over every rendered SVG and moves each
`<image>` down until it has 15px of clearance below the label above it. **Anyone
who regenerates diagrams must keep this call.** Without it the icons sit flush
against the text.

It exists because D2 gives no control over the clearance. What was tried:

| Attempt | Result |
|---|---|
| `icon.near` | Moves the icon but does not reflow anything around it. |
| `style.width` / `style.height` on the shape | Rejected by the layout engine. |
| Shape `width` / `height` | Inert for this purpose. |
| Smaller source icon | Normalised regardless of source size. |

Measured on one rendered node: the shape is `85x102`, the label baseline is
`y=25`, the icon spans `y=29.5..72.5`. That is a ~4.5px gap, with ~29px of EMPTY
space already inside the shape below the icon. The box was always big enough.
The icon was simply placed too high.

So the fix drops each `<image>` by whatever the current gap is short of 15px.
The shape is never resized, which leaves the border, the corner radius, and the
edge routing untouched. There is no configuration in `build.py` for the target
gap; if 15 ever needs to change, it is the `15.0` argument at the call site and
in the function default.

## Themes

Diagrams are **not theme-neutral**, and this is a decision, not an oversight.
Each theme is rendered separately with its own colours so the figure sits
correctly on the page it lands on. A single theme-neutral card was explicitly
rejected.

| Token | Light | Dark |
|---|---|---|
| Node fill | `#FFF3E4` | `#2D1608` |
| Node stroke | `#CE651B` | `#CE651B` |
| Node ink (text) | `#241005` | `#FFF7ED` |
| Edge stroke | `#C24E0C` | `#FF8C2E` |
| Icon stroke | `#7C3A0A` | `#FFD8A8` |
| Label font-size | `20` | `20` |

A practical consequence: a theme change is a **regeneration**, not a CSS
toggle. Change a colour in `THEME` and you must re-run the generator and commit
the new SVGs.

## The zero-JS contract

- A diagram is a build-time SVG referenced by `<img>`. There is no diagram
  JavaScript on this site and no CDN for one.
- **Both themes are in the DOM.** CSS shows one of them, keyed on
  `html[data-theme]`. The files are small and it means the theme flip needs no
  fetch, no swap, and no re-render.
- The theme attribute is a **manual toggle persisted in `localStorage`**. It is
  deliberately NOT `prefers-color-scheme`. A diagram that keyed off the media
  query would disagree with the rest of the page the moment a reader overrides
  their system setting.
- Because it is an `<img>`, the browser cannot reach inside it. That is the
  point, but it also means CSS cannot repair a diagram. Fix it in the
  generator.

## Keep diagrams portrait

A rendered SVG has ONE intrinsic size and is scaled by
`rendered / viewBox-width`, exactly as Mermaid's was. In a portrait reading
column a landscape diagram does not render small, it renders **illegible**. CSS
cannot fix this: the only choices are shrink everything or scroll. There is no
third option, and no post-render guard to paper over it.

So:

- **Use `direction: down`.** Every diagram in the `DIAGRAMS` dict does. A
  left-to-right chain of six nodes becomes a landscape ribbon in a portrait
  column.
- **Prefer short labels.** Label width drives shape width, and shape width is
  what makes a `down` graph drift wide.
- **Unconnected components get packed side by side** by dagre, regardless of
  direction. If you add a second component, connect it with an edge, even a
  dashed one carrying the real meaning. This is the single biggest width
  mistake available and it is inherited behaviour from dagre, not from D2.

Measured aspect ratios with `d2` v0.9.0 and the dagre layout engine:

| Diagram | AR |
|---|---|
| `01-ai-pipeline` | 0.46 |
| `02-delivery-pipeline` | 0.25 |
| `03-file-lifecycle` | 0.42 |
| `04-before-after` | 0.24 |
| `05-cutover` | 0.46 |
| `06-build-pipeline` | 0.34 |

## Known limitations

Being honest about what is currently wrong:

- **`02-delivery-pipeline` (0.25) and `04-before-after` (0.24) are very tall and
  narrow.** At the article measure they rely on horizontal scroll. Both are
  seven-node single-column chains, so the constraint is the node count, not the
  layout direction. Splitting either into two diagrams is the fix if it ever
  matters.
- The old authoring target was AR 0.3 to 1.6. Two diagrams are below 0.3. The
  target was written for Mermaid and the real output is what it is; do not treat
  0.3 as a hard gate.
- D2 emits an opaque background `<rect fill="#FFFFFF">` covering the whole
  canvas. Confirm it is not visible in dark mode before you consider this
  section closed.
- The generated SVG embeds a RELATIVE `href` to its icon
  (`assets/icons/light/<role>.svg`). Hugo fingerprints assets, so confirm that
  path still resolves in `public/`. If it does not, the icons are broken
  everywhere and it will not be obvious, because the shape, label, and border
  all still render.

## Verifying a change

There is no runtime to inspect, so verify the artefacts and then look at the
page.

```bash
rm -rf /tmp/d2check && mkdir -p /tmp/d2check
# inspect without polluting the working tree
sed 's#public/poc#/tmp/d2check#g' scripts/diagrams/build.py > /tmp/d2build.py
python3 /tmp/d2build.py
```

The generator prints one line per diagram per theme with `ok`/`FAIL`, the file
size, the aspect ratio, and the icon count. `FAIL` means D2 returned non-zero
and wrote nothing; the reason is truncated onto the end of the line. **Read the
output, do not just check the exit status.**

Then, on the article page, in both themes:

1. Every icon is visible and not flush against its label.
2. Icon strokes meet contrast against the node fill. The light-theme icon
   colour is deliberately not the brand accent for this reason.
3. No missing-image glyph.
4. No white panel behind the figure in dark mode.
5. The two tall diagrams scroll rather than squashing.

If you changed CSS, `rm -rf resources/_gen` first. Hugo caches the
concatenated stylesheet and a stale bundle will verify clean against a change
that is not there. A green build is not evidence.

## Why D2, and what Mermaid cost

**This section is history. Nothing below is current practice.** It is kept
because it is why the pipeline above exists, and because each of these was
expensive to discover and will be expensive again.

The last working Mermaid implementation is at commit `d564e15`. That is the
rollback point if you ever need to see it.

Mermaid is a fine library. The problem was that it renders on the client, which
means the site had to get the theme, the type scale, the icons, and the
legibility guard all right in the browser, where a green Hugo build proves
nothing.

What it cost:

1. **The double-render race.** Mermaid's ESM build auto-renders every `.mermaid`
   element on `DOMContentLoaded`. Our loader rendered too. Both claimed the same
   elements. The loader's source snapshot sampled the window after Mermaid had
   cleared the element but before it had rendered, captured `""` as the source,
   and its error-restore wrote `""` back. The source was destroyed permanently.
   **Both diagrams on a page failed silently behind a green build and an empty
   console.** The fix was a deliberately non-standard class name, `vm-mermaid`,
   which Mermaid's auto-run does not scan, so the loader became the only render
   authority. `window.mermaidConfig = { startOnLoad: false }` set before the
   module tag did NOT prevent the auto-run in the 11.x ESM build.

2. **One intrinsic size, and `useMaxWidth` scales it down.** There is no way to
   render a Mermaid diagram smaller; it scales the drawing, and the text with
   it. Four of six diagrams were painting labels at **3.8 to 5.0px** in the
   ~566px article measure, the worst being a 19:1 sliver. Nothing errored.

3. **Type scale needs `!important`.** Mermaid emits its theme rules
   ID-scoped (`#mermaid-<id> .messageText`, specificity 1-1-0), which beats any
   class-only selector from outside. Sequence-diagram sizes therefore silently
   did nothing without `!important`, while flowcharts looked fine, because the
   two emit different DOM. The `fontSize` option only reaches NODE labels.

4. **`themeCSS` cannot reliably restyle edge labels.** This is why the
   documented standard had to be enforced with `!important` and a browser
   console snippet rather than a config value.

5. **Mermaid cannot put an icon in a node.** Font Awesome node classes were
   removed in v10 and the markdown-image label syntax fails the flowchart lexer
   outright (`Lexical error ... Unrecognized text`). The workaround was to
   inject inline SVG into the label after render, keyed off an `@name` marker.
   Real per-node icons, which is what this site's figures are built around, was
   the one capability that genuinely argued for switching.

6. **No sequence-diagram primitive worth using.** Lifecycle and cutover were
   both redrawn as plain flows because the sequence view was not carrying them.
   And a theme flip required a full re-render of every diagram in the page.

The earlier written verdict on D2 (researched, in the session notes) was "not
worth it for six diagrams: new DSL, re-author everything, add a binary to CI,
and the SVG carries resolved hex so live re-skinning needs a token rewrite." That
verdict was right on its own terms. What changed the answer is point 5: the
icons stopped being decoration and became the primary identity channel, and
there was no version of the Mermaid workaround that got there without the
injection hack. The re-skinning objection in that verdict is why this pipeline
regenerates per theme instead of restyling in the browser.

D2 is MPL-2.0 and the CLI is a static Go binary. There is no runtime cost
because there is no runtime.
